# 既にあるものから書く

既にある文書に手を入れるときと、他人が書いた資料をもとに文書を作るときに読む。
新しく書く場合でも、その文書が後から引かれ続けるもの（README、仕様、参照資料）なら、「どちらの文書かを決める」と「経緯の置き場所」を読む。
他人の資料を使うなら、新規でも更新でも「他人が書いた資料をもとに書くとき」を読む。

## どちらの文書かを決める

後から引かれ、更新され続ける文書の条件は、いつ読んでも今の事実が書かれていることである。
読者は過去の経緯を知らず、知る必要もない。
基準は、初めて見た読者がその文書だけで理解できるかである。
これを**ストック型**と呼ぶ。
README、仕様、参照資料、Notion の常設ページが当たる。

その時点の報告、議事録、ログ、変更履歴は逆で、日付と経緯がそのまま意味を持つ。
これを**フロー型**と呼ぶ。
更新の仕方が逆になるので、書き始める前にどちらかを決める。

フロー型の記録は書き直さない。
日付を付けて項目を足す。
足すときに確かめるのは、足す箇所の前後と、同じ話題の既存の項目だけでよい。
以下はストック型の話である。

## 経緯の置き場所

| 書くこと | 置き場所 |
| --- | --- |
| 今の事実、決定、条件、規則、参照先 | ストック型の本文 |
| 判断に効く不採用案（採否と理由を1行） | ストック型の本文 |
| 今の判断に必要な変更の理由（いまの制約がどこから来たか） | ストック型の本文 |
| 相談や確認の経過、判断に不要な検討の過程 | フロー型の記録 |
| 残っている作業 | TODO やチェックリスト |

不採用案を本文に残すのは、読者が判断するための材料だからである。
どういう相談を経てそう決めたかは材料ではないので、フロー型に出す。

## 追記で済ませない

追記を重ねると、節の間で数値や条件が食い違い、同じ説明が複数の場所に残り、構成が会話の順になる。
どこが重要か分からなくなるので太字が増え、見出しは書いた本人にしか分からなくなる（経験則）。

確かめるときは、更新後のファイルだけを通して読む（[SKILL.md](../SKILL.md) の「読み直して削る」）。
文脈に依存する指示語と、どこにも書かれていない前提を探す。

## 編集の前に全体を読む

一部の行だけを表示したものを、全体を読んだ代わりにしない。
検索で当たった箇所だけを直すのも、シェルやスクリプトで書き換えるのも同じである。

## 直すか書き直すか

まず全体を点検する。
1か所の事実が変わっただけなら、その行を直す。
既存の節の構成では矛盾や重複を解消できないときだけ、節の分け方を含めて全体を書き直す。
節が1つ増えるだけで済むなら、構成は動かさない。

書き直すときは、読み手の立場で構成からやり直す。
元の節の順序が、日付順や思いついた順になっていないかを確かめる。

## 書き直しで内容を落とさない

書き直しは、黙って内容を落とす事故を起こしやすい。
元の項目は1つずつ、残した、不確か、意図的に省いた、のどれかに分類する。
未完成に見えたり、誤字があったり、他と矛盾しているからといって黙って落とさない。

矛盾を見つけたら、どちらが現在の値かを確かめてから直す。
確かめられないときは両方を書いて未確認と記し、依頼者に聞く。
黙ってどちらかを採らない。
この「未確認」は、依頼者に見せる下書きのあいだだけの印である。
マージする時点では残さず、確かめて直すか、本文から外して PR の説明か Issue に出す（[SKILL.md](../SKILL.md) の「確かさの書き分け」）。

元の文章を付録として文書内に残さない。
git やドキュメントツールが版を保つなら、履歴から取り出せる。
残すと文書は2倍になり、本文から外した経緯が付録として戻ってくる。
履歴の無い場所で他人の文章を整理するときだけ、置き換えの許可が出るまで元を別のファイルに残す。
依頼者が別の扱いを指示しているなら、それに従う。

## 他人が書いた資料をもとに書くとき

先に、どちらをしているのかを決める。
**その文書そのものを整理する**のか、**その資料を根拠にして別の読者向けの文書を書く**のかである。
扱いが逆になる。

整理するときは、元の文章の語彙と言い回しを残す。
整理は、構成と重複の始末であって、言い換えではない。
文体や語順を好みで書き換えない。
例外は、読者に通じると確認できない語だけである。
それ以外は、読みにくくても元の言い回しを残す。
[日本語の文と段落](japanese-prose.md) の語と文の規則は、自分が新しく書いた文にだけ当てる。
元の文の推敲まで依頼されているなら、元の文にも当ててよい。

別の読者向けに書き起こすときは、読者に合わせてよい（[SKILL.md](../SKILL.md) の「書き始める前に決めること」）。
そのとき保つのは表現ではなく、意味、出典、確かさの度合いである。
元の資料が推測として書いていたことを、断定に変えない。

整理する場合でも書き起こす場合でも、置き換えるのは、読者に通じると確認できない語である。
書いた人が作った造語、その資料の中だけで通じる略語、指す内容が一意に決まらない比喩が当たる。
読者の組織で日常的に使われている語は、こちらに分からなくても、確認したうえで残してよい。
「強い分類」ではなく「しきい値を超えた分類」と書く。
コードや設定の識別子になっていて置き換えられないときだけ、初出で定義して使う。
初出とは、その文書でいちばん最初に出る場所である。
一般に流通している語は、固い言い方でもそのまま残す。

再構成すると初出が動く。
元の資料で後半に定義されていた名前が、新しい構成の冒頭に出ていないかを確かめる。

書いた人にしか分からない前提（「前回決めたとおり」）は、確かめて具体に置き換えるか、未確認と記す。

曖昧なメモや書き起こしから、人や製品や社内ツールの表記や関係を確定しない。
確かめられないときは「〜は未確認」と本文に記すか、依頼者に確かめる未決点として挙げる。
読み取れたつもりの表記を黙って採らない。
