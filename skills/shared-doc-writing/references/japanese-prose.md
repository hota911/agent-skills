# 日本語の文と段落

日本語で書くときに読む。
書き始める前に目を通す。

ここにあるのは、日本語の語と文に固有の規則である。
段落と節の論証、見出しの付け方、言語に依らない削り方は [構成と論証を点検する](logic.md) にある。

「記法」の節だけは、言語に依らないものが混ざっている。
一文ごとの改行、コードブロック、脚注への降ろし、太字の上限と数え方がそれで、日本語以外で書くときもこの4つは効く。
同じ節にある読点、中黒、全角コロン、ダッシュ、全角約物と `**` の規則は、日本語に固有である。

## 文を整える

一つ一つの文は、読者がそこまでに読んだことだけで理解できるように書く。
これを妨げるのが、長い修飾節が主語や目的語の前に積み上がる文である（**逆茂木型**）。
読者は文の終わりまで何の話か分からない。
避けるための心得は3つある。

- 一つの文の中に、二つ以上の長い前置修飾節を書きこまない。
- 修飾節の中のことばに、さらに修飾節をつけない。
- 文や節は、前とのつながりが分かることばで書きはじめる。直前に出た語を受けるか、接続表現を置く。前を読み返させない。

直すときは、長すぎる文を分割し、前置修飾節が修飾していることばを前に出す。

## 記法

見出しに読点を入れない。
読点を入れたくなったら、2つのことを並べているか、見出しが長すぎる（[構成と論証を点検する](logic.md) の「見出しを点検する」）。
書誌情報も見出しに入れず、節の本文に置く。

- Git で管理する Markdown では、一文ごとに改行する。段落の区切りは空行で示す。Notion、Google Docs、Slack、GitHub の PR や Issue の本文のように、1回の改行がそのまま表示される場所や段落をひとまとまりで扱う場所では、文の途中で改行せず、段落をそのまま書く。
- コード、差分、ログ、設定ファイルの断片はコードブロックで示す。
- 用語の由来や定式化の名称など、本筋から一段外れる補足は、本文に並べず脚注（`[^ラベル]`）に降ろす。Markdown 以外の場所では括弧か別の節にする。
- 定義や分類の列挙は箇条書きで示してよい。定義される用語は太字にする。
- 用語を本文中で初めて定義・導入するときも、その語は太字にする。すでに導入した語を話題として指すとき、引用、通称には「」を使い、太字と使い分ける（初出の定義は太字、以後の言及は「」）。
- ダッシュ（em ダッシュ `—`、horizontal bar `―`、いわゆる2倍ダッシュ「——」）を日本語の地の文と見出しで使わない。同格や補足の挿入（「A——挿入——B」）は括弧（）に、言い換えや敷衍（「A——B」）は句点で二文に分けるか読点でつなぐ。範囲を示す en ダッシュ `–` や英語の複合語（`Curry–Howard` など）、コードブロック、書誌情報は対象外。
- 中黒（・）は、短い名詞の並列には使ってよい（「予算・期限・体制」）。文や節を並べるときには使わない。並列する語が長くなるときや、要素の中に読点が入るときも、読点か「と」でつなぐ。
- 用語とその定義を並べる箇条書きは、区切り線ではなく全角コロンで「**用語**：説明」と書く。
- 太字の `**` の内側に全角約物を接して置かない。CommonMark は、直前が約物で直後が文字の `**` を閉じと判定せず（開き側も対称の規則）、`は**「引用」**である` は生の `**` がそのまま表示される。括弧つきの語句を強調するときは、括弧ごと太字にせず中身だけを太字にする（`「**中身**」`）。約物が `**` の外側にある `**用語**：説明` は、この規則に当たらない。
- 太字の上限（「飾りを落とす」にある）に、用語を定義するための太字は数えない。

## 段落をつくる

段落の組み立ては [構成と論証を点検する](logic.md) の「段落ごとに論証を進める」にある。
日本語に固有なのは1つである。

- 段落の話題は最初の文に置く。日本語は修飾節が前に来るので、意識して置かないとトピックが段落の末尾に回る。

## 語を選ぶ

- 文体（ですます調か、である調か）は相手との関係で決める。決まらなければ依頼者に聞く。1つの文書の中では揃える。
- 読者を「あなた」と呼ばず、役割名（「開発者」「読者」）で書く。二人称の呼びかけは、場面への導入（「〜としよう」）など限られた要所にとどめる。
- 対象を指す語は具体的に選ぶ。「AI」「ツール」のような広い語でぼかさない。
- 定式化や術語（契約、不変条件など）を導入したら、以後はその語で通す。「文脈」「ツール」「AI」のような曖昧語に後退しない（定式化する前の導入語として「文脈」などを使うのはよい）。
- 術語と訳語は、その分野で慣用されている語を選ぶ（プッシュ通知は「配送」ではなく「配信」、など）。意味の近い漢語を一般語の感覚で充てない。
- 術語の響きを持つ語を、術語でない場面に流用しない（システムから人間までの連なりを「経路」と呼ぶ、など）。「届くまでの流れ」「あいだに何があるか」のように普通の言い方で書く。

## 飾りを落とす

中身を足さずに「ちゃんと書いている感」だけを付ける型がある。
書き終えてから、自分の文章にこの型が出ていないか探す。

- 溜め（「ここには〜が潜んでいる」）や修辞疑問で導出を演出しない。説明で足りる箇所では、そのまま述べる。
- 本文中の太字強調を多用しない。誤読を防ぐ否定や節の帰結など、論理の要所に限り、一節に一、二箇所まで使ってよい。それ以外は文の順序と構造で際立たせる。
- 帰結の列挙によって事故や危険を煽らない。
- 慣用表現をひねった言い回し（「知識を体に入れる」など）や、指す内容が一意に決まらない比喩（「報告の外側に世界が広がっている」など）を使わない。平易な動詞でそのまま言う（「身につく」「気付く機会が減る」）。

次の言い回しは使わない。

- **予告と総括**：「ここでは〜について見ていく」「まとめると」「要するに」（直前の言い換えだけのとき）、「〜に他ならない」。ただし、冒頭でその文書が何であるかを告げる一文は、これに当たらない（[SKILL.md](../SKILL.md) の「冒頭に置くもの」が要求している）。
- **姿勢の宣言**：「正面から扱う」「正面から回収する」「正面から見る／書く／立てる」。中身の代わりに姿勢だけを宣言している。
- **空虚な形容**：「重要な」「不可欠」「核心的」「鍵となる」「根本的な」（主張の中身を説明せず強調だけする）、「多角的」「包括的」「総合的」（何をどう見たかを書かない）
- **空虚な動詞**：「掘り下げる」「深掘りする」「言語化する」（何をどう書いたかを示さず終わる）、「触れる」「言及する」（一段落で済ませるだけ）
- **接続の型**：「〜において」「〜という側面から」「〜の観点から」（新情報なし）、「さらに」「また」「加えて」の連打。ただし、対比や転換を示す接続表現は省略しない。
- **中身のない強調**：「非常に」「極めて」「大いに」

悪い例：「本稿では、〇〇の理論を正面から扱う」「多角的に分析すると、重要なのは〜である」。
良い例：「本稿では、〇〇の理論を扱う」「評価が難しいのは、正しさを誰が知っているかが決まらないためである」。

言語に依らない削り方（同じ主張の繰り返し、節どうしの重複、中間段階の説明、概念を出す順）は[構成と論証を点検する](logic.md) にある。
ここは日本語の言い回しに固有のものを挙げる。

- 何かを描写した直後に、その内容を要約し直さない。意味づけの一文だけを置く。
- 同じ論理的役割を持つ短い並列の事実は、文を分けて重ねず一文にまとめてよい。その事実群の論理的地位は文頭の語で示す（「当然、経理部の月次処理も顧客の支払いも〜」）。比較する、あとから個別に参照する、項目ごとに条件が違う、のどれかなら一文にせず一覧にする。文書の冒頭に置く案内も一覧にする（[SKILL.md](../SKILL.md) の「一覧にするか続いた文にするか」と「冒頭に置くもの」）。
- 数文にわたる議論を一文に圧縮できるなら、圧縮した一文だけを残す。
- 接続や評価のためだけの文（「それ自体はよいことである」など）を置かない。
- 想像上の読者との問答（問いを立てて一語で答える形など）を修辞として使わない。主張はそのまま述べる。読者の反応を演じて応答する形（「〜と感じたかもしれない。そのとおりである」）も避け、譲歩は地の文で簡潔に行う。
- 読者が抱きそうな発想を、メタな枠取り（「ここまでの話には自然な続きがある」「〜という発想である」）で紹介しない。その発想自体を直接書く。読者の疑問なら疑問文のまま書いてよい。
- 判断に関係しない自己弁護を書かない（「専門外だが」「力不足ながら」など）。調査の範囲や確かさを限る事情（「調査期間が短く、月末の処理は観測できていない」）と、「〜と仮定した」「未検証」は、読者が判断に使うので残す。
- ためらいのある弱い述語（「有効な対策であり」など）で済ませない。本文内の根拠で確定していることは具体的に言い切る。断定に直してよい条件は[構成と論証を点検する](logic.md) にある。
