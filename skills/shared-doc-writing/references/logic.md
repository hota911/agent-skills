# 構成と論証を点検する

書き始める前に一度目を通し、書き終えてから点検に使う。
見出しの付け方、段落の組み方、語を定義する順、概念を出す順は、書き終えてから直すと構成の書き直しになる。
言語に依らない。

読み手の反論を先回りして、次を点検する。

- 論理の鎖の環をはぶかない。自分にとって自明なために書き落とした条件が、読者には欠けて見える。「管理者権限を持つ利用者の場合には」と書くべきところを「利用者の場合には」と書いていないか、条件を一つずつ確かめる。くどいと感じても、環は省かない。
- 推量、可能性、読者の疑念、反実仮想として書かれている文を、機械的に断定へ変えない。「かもしれない」「だろう」は、根拠なく主張を弱めている場合だけ削る。事実未確認の可能性、ログからの推定、読者が抱きそうな疑念を表す場合は、その不確実性を保つ。断定に直せるのは、本文内の根拠によって命題が確定している場合に限る。悪い例：「提示し続けているかもしれない」を「提示し続けている」に変える。良い例：「提示し続けている可能性がある」。
- 異なるものを「同じ」とまとめない。区別すべき対象（別々の決定、別々の原因、種類の違う問題）を一括りの言葉でくくらない。悪い例：相互依存する三つの未決事項を「同じ決定を別々に下していた」と書く。良い例：「どれも別々の決定であり、しかも互いに依存している」と切り分ける。
- 複数の要因がある事象を、単一の原因に還元しない。例が複数種類の問題を含むなら、それぞれを切り分け、どの道具がどれを説明するのかを対応づける。
- 節をまたいで、同じ概念の扱いを一致させる。ある節で「自動で決まる」と分類したものを、別の節で「人の承認を経て決まる」と書かない。分類、定義、用語の地位は全体で揃える。
- 因果を主張するときは、その機構（なぜそうなるのか）を一文で示す。「AだとBになる」とだけ書いて理由を省略しない。悪い例：「手順で分けると変更が全体に波及する」。良い例：「各工程がデータを受け渡すための表現を共有してしまい、その表現を変えると全体に波及する」。
- 検出、保証、解決を「必ず」できるかのように書かない。成り立つ条件を書く（「〜が成り立つときに限り」）。述語をやわらげて済ませない。
- 主張は、挙げた例が実際にその全体を支えているかを確認する。例が主張の一部しか支えないなら、主張の範囲を例に合わせて狭める。
- 譲歩や限定（「ただし」「確かに」「とはいえ」）を置いたら、その後で必ず論を進める。逆接で終えて宙吊りにしない。譲歩で認めるのは事実の確認にとどめる。あとで訂正する内容を自分の声で因果として断定すると、自己矛盾になる。表面的な診断を一度認めたいときは、読者や通説の声に帰属させる（「〜と要約できてしまうかもしれない」）。
- 読者に既知と確認できない名前と、この文書独自の意味で使う名前は、定義と対象範囲を述べてから使う。まだ導入していない概念や文書名を、先回りして持ち出さない。
- 新しい造語、ラベル、比喩を作らない。すでにある言葉で言う。名前が要るなら依頼者に聞く。
- 人名、製品名、社内ツール名の表記を推測で決めない。確かめられないときは、確認できた綴りのまま書くか、未確認と記す。
- 複数の概念を一つの上位語にまとめるときは、命名の直前に、何を共通点としてまとめるのかを一文で述べる。同じ分類に入ることと、同じものであることは区別し、判断に効く違いは残す。切り分けの逆の操作にも橋を架ける。
- 読者が実際にその誤解をしうると分かるとき（依頼者から示された、過去に生じた、本文の表現が直接招く）に限り、誤った解釈を明示的に否定してから本当の理由を述べる（「その理由は『〜だから』ではない。〜だからだ」）。まず元の表現を直せないかを見る。想像した誤解を並べない。
- 何かを否定・限定するときは、否定する命題そのものを引用符で正確に書き出す（「明文化されていればすべてを任せられる」を意味しない、など）。「何もかもが解決するわけではない」のような漠然とした否定で済ませない。「AではなくB」と否定するなら、否定の根拠を一文添える。反実仮想（「もしAなら、〜だっただろう」）が使えることが多い。

## 段落ごとに論証を進める

段落は論証の一歩であり、読者は段落単位で論理を追う。

- 一つの段落には一つのトピックだけを置く。進行（調査、報告、検証、評価）が複数混ざった長い段落は、一歩ずつの段落に分割する。
- 段落の最初の文を読めば、その段落が何の話かわかるようにする。
- 段落の先頭で、前の段落との論理関係を接続表現で示す（「であれば」「実際」「しかし」）。
- 主流から外れてわき道にはいるときは、はいるところでそのことを書く。わき道の話を読み終わってから主流との関係が分かる、という書き方をしない。わき道が長くなるなら脚注に降ろす。
- 一つの節の中では、論証を一方向に進める。反論と疑念の処理を終えてから、その節の結論を一度だけ置く。節の途中で結論を出し、反論を処理し、また結論を言い直す形にしない。各節の冒頭に、その節の結論を置く必要はない。置くのは話題である。文書全体としては結論が冒頭に来る（[SKILL.md](../SKILL.md) の「冒頭に置くもの」）。文書の冒頭に置く結論と、本文の節が置く結論は別のものである。

## 読者の負荷を減らす

- 後で参照する必要のない固有名（ファイル名、関数名、識別子）を出さない。「仕様書」「金額計算のユーティリティ」のような一般的な言い方で済ませる。
- 抽象的な言い回しの指す内容が文脈から一意に決まらないときは、括弧による同格挿入でその場で特定し、読者に前を読み返させない。
- 新しい例を追加して、読者が保持すべき文脈が増えるときは、前の例と何が違うのか、なぜもう一つ必要なのかを先に書く。
- 節の導入に、これから扱う内容に関係しない詳細を詰め込まない。
- 例の中でも、その節の問いと帰結に関係しない詳細を省く。装飾的な精度（時刻、HTTP ステータス、カバレッジ率など）が典型である。議論に必要な具体は残す。

## 冗長を削る

- 同じ主張を言い換えて繰り返さない。一つの主張は一度だけ書く。冒頭で結論を示し、本文でそれを論証するのは繰り返しに数えない。
- 隣接する節が同じことを別の角度で述べているなら、役割が重複している。片方に吸収して一つの節にまとめる。
- 読者が自力で補える中間段階の説明は書かない。ただし「論理の鎖の環をはぶかない」は守る。線引きは、省いても読者が同じ結論にたどりつけるかで決める。

## 見出しを点検する

- 見出しは、その節が答える問い、扱う対象、またはその節が定める規則を指す句にする。情報量のない見出しや、作業の手順だけを述べる見出し（「例に戻す」など）にしない。
- 見出しは短くする。具体にするために構文を複雑にしない。節の見出しに2つの要素を並べない。「AとB」「Aと、そのB」の形にしたくなったら、片方に寄せるか、上位の語でまとめる。悪い例：「数字と、その確かさ」「変えられない条件と、見直せる条件」「3つの案と、いまの採否」。良い例：「前提にしている数字」「変えられない条件」「検討した3つの案」。例外は2つで、節が答える1つの問いを選択肢の形で書いたもの（「一覧にするか続いた文にするか」）と、扱う範囲を示す文書の表題（`#` の行）である。
- 見出しに章番号をつけない（「## 1. 背景」「## 2. 経緯」など）。節の追加、削除、入れ替えのたびに番号の振り直しが必要になり、「§3」のような番号参照も壊れる。節への参照は節名で行う。ただし、読者が指摘を返す目印として、未決の論点や前提には番号を振ってよい（Q1、前提3 など）。
