# 共有文書の書き方

- 何の文書か：他人に読ませて反応を得るための文書の書き方である。言語には依らない。
- 読むと何が分かるか：読者と主題の決め方、冒頭に置くもの、指摘が返る形、確かさの書き分け、一覧と文の使い分け、書かない作業経緯、推敲、出し方。

目的は2つある。
読まれること、そして判断かレビューを求める文書なら、読んだ人が指摘か承認を返せることである。

立っている前提は、読者が忙しく、説明の場を毎回は取れず、読まない理由を探している、というものである（経験則）。

依頼者しか知らない値は、聞くか、文書の中で未定と書く。
期限、期限までに返事がなかったときの扱い、返事先、予算、変えられない条件、連絡先、文書の著者を、もっともらしい値で埋めない。
この禁止は、ほかのどの節が「書く」と指示している項目にも優先する。

最初の節は書き始める前に決めること、最後の2つの節は書いたあとにすること、あいだは本文が満たすことである。
場面によっては、別のものも読む。

| 場面 | 読むもの |
| --- | --- |
| 日本語で書く（書き始める前と、読み直すとき）。日本語以外で書くときも、「記法」の節にある言語に依らない4つは読む | [日本語の文と段落](references/japanese-prose.md) |

| GitHub の PR の説明を書く | [PR の説明](references/pull-request.md) |
| 規則の由来を確かめる | [出典](references/sources.md) |

## 書き始める前に決めること

次の5つを決めてから書く。
依頼や資料から決まらないものは、推測で埋めず、書き始める前に依頼者に聞く。
書き上げてから聞くのは、依頼者の時間を使う。

- 読者：誰が読むか。承認が要るなら、その読者に決める権限があるか。
- 役割：読者がこの文書に何を期待しているか。提案なら、検討したことを並べるのではなく、その案の価値と実現の見込みを判断する材料を出す。
- 主題：1つに絞る。目的の外で分かったことは、判断に影響するなら付録か別の文書にする。
- 目標規定文：伝える結論か、読者に判断してほしい問いを1つの文にする。結論が未決なら無理に作らず、問いと、判断に要る材料を決める。
- 求める反応と確かさ：論点ごとに、指摘が欲しいのか承認が欲しいのか。調べたことのうち、どれが確かめたことで、どれが置いた前提で、どれが推測か。

本文を書く前に、この5つと見出しの並びを数行の骨子にして依頼者に示し、合意を取る。
聞きたいことと、迷っている点への自分の案も、このときに出す。
長い文書では、骨子のあと、見出しごとの要点を箇条書きにして示し、そこで直してから本文にする。
短い文書や、依頼がすでに骨子を含むときは省いてよい。

読者が決まると、長さと詳しさが決まる。
専門家はやり方の根拠と前提と採らなかった選択肢を見る。
決裁者は何が決まるか、影響、期限を見る。
1つの文書に混ぜるなら節を分け、節分けで読み分けにくいなら文書を分ける。

読者がすでに知っていることは書かない。
読者が知らない前提は書く。
線は、読者が知っているかどうかで引く。
自分が調べて知ったかどうかではない。
用語は読者の組織の言い方に寄せ、自分の側の略語は使わないか初出で定義する。
文体の手本になる既存の文書があるなら、依頼者に聞いて合わせる。

通読してもらう文書（提案、検討案、調査結果、PR の説明）は、読者が5分で読み終わる量（日本語でおよそ2,000字、英語でおよそ1,000語）を上限の目安にする。
上限は、主題を絞る制約でもある。
README、仕様、参照資料のように引いて使う文書には上限を置かず、必要な人が必要な箇所だけを読めるようにする。

途中で主張が変わったら、目標規定文を書き直し、本文も書き改める。
執筆中に根拠の不足が分かったら、追加で確かめるか、未確認と記す。

## 冒頭に置くもの

読者は、読む価値があるか分からないまま読み始める。
頭にあるのは、これは自分に関係があるのか、読むと何が分かるのか、自分は何かする必要があるのか、自分に分かる言葉で書かれているのか、である。
最初の数行でつまずくとそこで終わる（経験則）。
社外や業務委託の相手では、「この人の文書は読む価値がある」が読む前に成り立たないので、文書ごとに冒頭で示すしかない。

冒頭に置くのは、何の文書で、読むと何が決まるか、誰に何をしてほしいか、どこまで進んでいるかである。
ここでいう冒頭とは、表題と、最初の見出しより前の部分を指す。
見出しの前に何も置かない文書では、最初の節を指す。
当てはまらない項目は置かない。
README、仕様、参照資料のように引いて使う文書には、してほしいことも進捗も無いので、何の文書かと読むと何が分かるかだけを置く。
無い依頼や無い進捗を作らない。

この案内は、読者が自分に関係するものだけを拾う項目なので、続いた文にせず、短い箇条書きか表にする。
読者は冒頭を読まずに眺めるので、段落にすると、どれが自分に関係するかを探すために全部読むことになる（経験則）。
Markdown では、各項目を `- ` で始めるか、表の行にする。
行頭に記号の無い「項目：値」の行を並べただけでは、1つの段落として表示されるので、箇条書きにならない。
項目名は用語の定義ではないので太字にせず、全角コロンでつなぐ（「対象：…」）。

結論と、それを支える根拠は、この案内の項目に切り分けず、案内のあとに短い続いた文で置く。
条件つきの結論は、条件と結論を同じ文に書く（「負荷試験が通る限り、A 案にする」）。
結論から条件や留保を切り離さない。
根拠を詳しく述べるのは本文からである。

**読者に既知と確認できない名前（モード名、略語、段階名、ツール名、識別子）は、文書の中で最初に出る位置で、その場で定義するか言い換える。**
元の資料、コード、会話から持ち込んだ名前が、まずこれに当たる。
後の節の定義で代用しない。
結論や論点を前へ移したときは、それが使う名前の定義も一緒に移す。
冒頭で名前が要らないなら、名前を出さず、資料から確認できる意味を普通の言葉で書く。
意味を確認できないときは、推測で言い換えず、依頼者に確かめるか、未確認と記す。
冒頭に置く「どこまで進んでいるか」は、元の資料の名前をいちばん持ち込みやすい箇所なので、とくに確かめる。

表題と冒頭だけで、その文書の結論と要点が分かるようにする（**重点先行主義**）。
結論がある文書なら結論を、未決の文書なら判断してほしい問いと、いま分かっていることを置く。
無い結論を作らない。
表題は内容を特定する具体的なものにし、分類名だけで済ませない。

**結論は冒頭に置く。背景から順に結論までなぞる形にしない。**
冒頭には、求める返事をするのに要る結論と根拠を短く置き、詳しく見る必要がある箇所へのリンクを添える。
そのうえで概観から細部へ進む。
冒頭の短い記述で全体がつかめれば、読者は細部を受け取れる。
承認だけが欲しい文書なら、読者が冒頭だけで承認を返し、本文を開かないことは失敗ではない。
質を見てほしい文書では、冒頭に見てほしい箇所への導線を置く。

読む価値は読者が判断する。
「重要な」「興味深い」と書いて判断を押しつけず、判断の材料を出す。
この類の形容詞を仕事の文書に混ぜない。
示し方は「調査しました」ではなく、読むと何が決まるか、何が分かるかである。

## 指摘が返る形にする

この節は、読者に判断かレビューを求める文書に効く。
README や仕様のように、使い方を説明するだけの文書の本文には、未決の論点も期限も要らない。
その変更をレビューしてもらうなら、依頼は本文ではなく共有メッセージか PR の説明に置く。

読んだ人が返事を書くための入口は、こちらで作る。

未決の論点を、文書の前のほうに疑問形で出す。
これは迷った過程ではなく、いまの状態である。
「AとBのどちらにするかを、この観点で決めてほしい」と書いてよい。
採らなかった選択肢は、判断に効くものに限って、採否と理由を1行で添える。
まだ決めていない選択肢には採否を書かず、判断してほしいと書く。
どちらも読者が判断するための材料であって、検討の経過をたどるためではない。

**変えられない条件を書く。**
予算、期限、使えない技術、触れない既存仕様。
自分が暫定的に範囲外にしたものは、変えられない条件と並べず、見直せることを添えて分けて書く。
分けないと、読者はその判断を疑えなくなる。
制約が分からないと、読者は「もっと良いやり方があるが、何か事情があって使えないのかもしれない」と考えて、何も言わずに終わるおそれがある（経験則）。

答える手間を減らす。
見てほしい箇所と観点は名指しする。
「全体を見てください」では、要件とアーキテクチャと運用コストのどれを見ればよいか決まらない。
どこに返事を書けばよいか（コメント先、返信先）を書く。
期限と、期限までに返事がなかったときにどうするかも書く。

**問いの形は、何が欲しいかで変える。**
決めてほしいなら選択肢にする。
質を見てほしいなら選択肢にしない。
「AとBのどちらか」と聞くと、「前提が違う」「比較軸が足りない」「どちらも成立しない」という指摘が返りにくくなる（経験則）。
質を求めるときは、見る対象だけを絞り、答えの形は絞らない。

してほしいことは、1つの論点につき1つにする。
同じ論点について指摘と承認を同時に求めると、読者はどちらを返せばよいか決めにくい（経験則）。
文書全体としては、方針への承認を求めながら、個々の未決点について指摘を求めてよい。
条件でつないだ1つの依頼（「問題があれば指摘、なければ承認」）は、どちらを返すかが読者の側で決まるので成り立つ。

## 確かさの書き分け

**検証した事実、置いただけの前提、未検証の推測、迷っている選択肢を、同じ調子で書かない。**
生成した文章は、確かめたことと確かめていないことを同じ強さで言い切りやすい（経験則）。
全体が確定済みに見えると、読者は指摘する箇所を見つけにくい（未検証の仮説）。

確かさは、文の調子ではなく形で示す。
前提は「〜と仮定した。検証していない」とその場に書く。
数字は実測と見積もりを分け、見積もりには根拠と幅を書く。
確かさの区別がいくつも並ぶなら、一覧にして本文から参照する。

やっていないこと、省いた範囲、失敗したことを書く。

**裏打ちの無い意見を書かない。**
根拠を示せない判断や推測を混ぜない。
書くなら、何を根拠にしているかを添える。
出典（どの文書、どの節、どの行）を書くのは、形式を整えるためではない。
他人の発言や文献の記述を、その人の発言、その文献の記述としてそのまま伝えれば、読者は原典に当たって本当にそう書いてあるかを確かめられる。
ここで事実として扱えるのは「その資料がそう述べていること」であって、述べている中身が成り立つことではない。
資料の中の推測や留保は、推測や留保のまま運ぶ。
自分の推論にはその裏付けが無いので、資料がそう書いていることとして書かない。

## 一覧にするか続いた文にするか

一覧にするのは、比較する、あとから個別に参照する、項目ごとに条件が違う、のどれかに当たるときである。
選択肢、条件、比較、読者別の導線、確かさの区別が当たる。
どれにも当たらない短い並列の事実は、一文にまとめてよい。
例外は冒頭に置く案内で、短くても一覧にする（「冒頭に置くもの」）。
判断の筋道は続いた文で書く。
背景と考察と結論を箇条書きの切れ端にすると、論理の粗さが隠れる（経験則）。
表や箇条書きの前後に、その内容を繰り返す文を置かない。

## 自分の作業経緯は書かない

書かないのは作業の時系列である。
「相談した結果」「調査したところ」「まず設定を疑い、次にログを見た」。
どう作ったかは書き手の関心であって、読者の関心ではない。
会話の文脈に依存する語（「今日」「この前」）も同じで、日付を書く。
「上記」のように、節を動かすと指す先が変わる語も使わず、節の名前を書く。

今の判断に要るものは、過去の話でも書く。
結果として何を確かめたか（「負荷試験で毎秒800件まで確認した」）、なぜその変更が要るのか、いまの制約がどこから来たのか。
再レビューを頼むときは、前回から何が変わったかを書く。
読む範囲を決める材料になるからである。
線は、読者がいま判断するのに要るかどうかで引く。
書き手がそこを通ったかどうかではない。
自分がたどった紆余曲折ではなく、結論から振り返って見つかるいちばん簡明な道に沿って書く。

落とした経緯には行き先がある。
判断に効く不採用案と、いまの制約がどこから来たかは本文に残す。
相談や確認の経過と、判断に不要な検討の過程は、日付を付けて足していく記録（議事録、作業ログ、プロジェクトの log）へ出す。
残っている作業は TODO やチェックリストへ出す。
後から引かれ続ける文書での分け方は[既にあるものから書く](references/updating.md) の「経緯の置き場所」にある。

## 読み直して削る

書き上げたら、読者の目で読み直す。
会話の履歴や元の版を前提にせず、その文書だけを読む。

まず、名前の点検を単独で行う。
表題から順に読み、読者に既知と確認できない名前（略語、モード名、段階名、ツール名、識別子）をすべて書き出す。
それぞれが「冒頭に置くもの」の規則どおり、最初に出る位置で意味を持っているかを確かめる。
後の節に定義がある場合も、どこにも定義がない場合も、同じく直す対象である。

そのうえで、次を確かめる。

- 冒頭だけを読んで、何の文書か、読むと何が決まるか、自分は何をすればよいか、どこまで進んでいるかが分かるか
- 確かめたことと確かめていないことの区別が残っているか
- 依頼者から聞いていない値が、もっともらしい値で埋まっていないか
- 判断かレビューを求める文書では、次も確かめる
  - 未決の論点が、実在するものだけ挙がっているか
  - 見てほしい箇所と観点、返事の書き先、期限、期限までに返事がなかったときにどうするかが書かれているか
  - 変えられない条件と、見直せる暫定の条件が書き分けられているか

そのうえで、[構成と論証を点検する](references/logic.md) の項目を一つずつ本文に当てる。

書き終えたら、削るためだけにもう一度通読する。
削るのは、繰り返し、作業の時系列、読者の分野で一般知識にあたる前提、読者の負荷になる詳細（[構成と論証を点検する](references/logic.md) の「読者の負荷を減らす」）である。
その検討に固有の前提（対象のバージョン、前提に置いた制約）は、自明に見えても残す。
判断の根拠と数字も残す。

上限を超えたぶんは、消すのではなく付録か別の文書に移してリンクする。
**結論を信じてよいかの判断に要る主要な数字と幅は本文に置き、それを導いた分析の詳細は付録に置く。**

推敲で、確かさの書き分けを断定に変えない。
「〜と仮定した」「未検証」を、文を締めるために削らない。

依頼者から指摘を受けたら、その1か所だけを直して終えない。
同じ種類の箇所を文書全体から探し、まとめて直すか、直してよいかを聞く。
指摘が方針に関わるとき（結論を変える、節を消すなど）は、ほかの節への影響と選択肢を示して提案する。

## 出すまでが書く仕事

置くだけでは読まれない。
文書と、それを読ませるメッセージを対で作る。
読者は文書の全体を読まないが、メッセージに書かれた箇所までは読み、そこから文書に入ることが多い（経験則）。

本文を読んでほしい文書では、メッセージに書くのは要約ではなく導線である。
要約だけで用が足りると、本文は開かれない（経験則）。
冒頭だけで承認が返ればよい文書なら、メッセージが要約でもかまわない。
書くのは、何の文書か、誰にどの節を何のために見てほしいか、いつまでに何が欲しいか。
宛先をまとめて「ご確認ください」と書かない。
読者ごとに見てほしい箇所は違う。
スクロールせずに読める長さにする。

メッセージに、リンクを開けないときの連絡先を書く。
権限を自分で確かめられないなら、依頼者に確かめてもらう。
