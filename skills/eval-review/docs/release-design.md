# リリース判定タブの設計メモ

## 目的

ゴールデンデータセットでの評価結果から、現行モデルに対する複数の候補モデルそれぞれについて、リリースしてよいかを判定する。判定基準は設定に書き、数値の集計と判定はスキルの固定コードが行う。AI が書くのは設定だけである。

対象外とするもの：過去リリースの推移、統計的検定を判定基準に使うこと、チームでのレビュー結果の共有保存（記録の書き出しで代える）。

## 入力

現行（`data.csv`）と候補（新設の `data.candidates`）を、同じ id で突き合わせる。

```json
"data": {
  "csv": "current.csv",
  "label_a": "現行",
  "candidates": [
    {"file": "cand_b.jsonl", "label": "候補B"},
    {"file": "cand_c.jsonl", "label": "候補C"}
  ]
}
```

`candidates` は、今の `csv_b` / `label_b` を置き換える（候補1つの比較も `candidates` に1件書く）。同じことを書く方法を2つ残さないためである。`csv_b` を含む設定は、書き換え方を示すエラーにする（2026-10-11 リポジトリのオーナーが廃止を了承）。

## 判定基準

`release.criteria` に、次の4種類を並べる。どの基準も候補ごとに評価する。

| 種類 | 書き方の例 | 意味 |
|---|---|---|
| 絶対値 | `{"type": "absolute", "metric": "correct", "min": 0.85}` | 候補の集計値が範囲内にある（`min` / `max`） |
| 現行比 | `{"type": "relative", "metric": "cost_usd", "max_worse_pct": 10}` | 現行からの悪化が上限以内（`max_worse`：指標の単位、`max_worse_pct`：割合） |
| 悪化件数 | `{"type": "regressions", "max": 3}` | 悪化と判定された項目の数が上限以内 |
| 重要カテゴリ | `{"type": "critical_categories", "categories": ["safety"]}` | 指定カテゴリで悪化した項目が0件 |

指標の集計と「悪化」の定義は、今の比較ビューと同じ規則（`aggregate`、`better`、`regression_threshold`）を使う。

人によるレビューは `release.review_labels`（既定は `["許容", "不可"]`）で、悪化した項目に1件ずつラベルを付ける。

## 判定

候補ごとに、次の順で決める。

1. 自動の基準を1つでも満たさないか、レビューで「不可」が1件でもある → 出さない（NO-GO）
2. 自動の基準はすべて満たすが、レビューしていない悪化項目が残る → 要レビュー
3. それ以外 → 出してよい（GO）

要レビューは独立した判定として扱う（2026-10-11 リポジトリのオーナーが決定）。

## 画面

- 候補ごとの判定カード：判定、満たさなかった基準、未レビューの件数。
- 候補 × 基準の表：実際の値、基準値、合否。合否は色だけでなく記号と文字でも示す。セル・判定・判定カードの理由を押すと、表の下にその判断の根拠（集計値と k/n、n、基準値、差分、悪化項目とその理由・レビュー結果、レビューと比較への移動）を表示する。
- 各指標の件数（n）と、現行との差の95%区間を表示する。判定には使わず、差が誤差の範囲かどうかの目安にする。
- 候補を選ぶと、その候補の悪化項目のレビュー画面と、既存の比較ビュー（現行 vs その候補）に移れる。

## 記録の書き出し

Markdown と JSON で書き出す。含めるもの：タイトル、書き出した日時、データのファイル名、判定基準、候補ごとの集計値と合否、悪化項目ごとのレビュー結果とメモ、判定。

レビュー担当者の名前とレビュー日時は記録に含めない（2026-10-11 リポジトリのオーナーが決定）。

レビュー結果は今のレビュータブと同じく閲覧者のブラウザに保存されるため、他の人と共有するときは書き出した記録を渡す。

## 判断をまとめたレポート

レポートは HTML に含める（2026-10-11 リポジトリのオーナーの依頼）。流れは次のとおりである。

1. ダッシュボードを作り、人が悪化項目をレビューして、判定の記録（JSON）を書き出す。
2. AI が記録と元データを読み、レポートを Markdown で書く。数値は記録から引用し、計算し直さない。
3. 設定に記録とレポートを指定して作り直す（`release.record`、`release.report`）。HTML には「レポート」タブが加わり、レビュー結果も記録から埋め込まれる。HTML を1つ渡せば、受け取った人もレビュー結果を含めて同じ判定を見られる。

レポートの構成：結論（候補ごとに出してよい／出さない／要レビュー）、理由（満たさなかった基準、「不可」の項目）、注意点（差が誤差の範囲の指標、件数の少ないカテゴリ）、次にやること。

表示と検証：

- Markdown は見出し・段落・箇条書き・表・強調だけを扱う小さな変換をスキル側に持ち、文字は textContent で入れる。HTML タグは文字として表示する。
- レポートの先頭に候補ごとの判定を決まった形式（frontmatter）で書かせる。作り直すとき、ビルドはその判定と、記録から計算し直した判定を突き合わせ、食い違えばエラーにする。本文中の数値までは突き合わせない。
- 作り直した後に画面でレビューを変えた場合は、レポートが古い記録に基づくことをレポートタブの先頭に表示する。

## 評価

架空データで、現行と候補3つ（GO になるもの、重要カテゴリの悪化で NO-GO になるもの、要レビューになるもの）を用意し、評価ケースに追加する。
