# 実験結果の共有（仮説検証）の設計メモ

状態：実装済み（2026-10-11）。キーと記録の形式は [references/config.md](../references/config.md) の `experiment`、レポートの書き方は [references/experiment-report.md](../references/experiment-report.md) にある。実装時に次の2点を加えた。記録には `hypothesis` に加えて `verdict_labels` も入れ、ビルド時に設定と照合する。1つの設定に `release` タブと `experiment` タブを同時に書くことはできない（レポートと記録がどちらの判定のものかを一意にするため）。

## ユースケース

SKILL.md の用途表に、5つめの用途として次の行を加える。

| Job | Tabs | What the reader gets |
|-----|------|----------------------|
| 実験結果の共有（仮説検証） | `experiment`（+ `report`）, `compare`, `overview`, `table` | 仮説と判断基準、ベースラインに対する各条件の結果（差と95%区間）、悪化した項目のレビュー、結論を書いたレポート、Markdown の書き出し |

- 目的：データサイエンティストが行うような実験（新機能、モデルの変更、新しい手法）で、仮説を立て、改善したかどうかを判断する。
- 読み手：実験した本人が、結果をチームなどに共有する相手。データを見ていない人が読んで判断の根拠まで追えることを目標にする。
- 成果物：HTML 1つ。レポートは HTML の中に置き、Google Docs や Notion に貼るために Markdown でも書き出せるようにする。

以上は 2026-10-11 にリポジトリのオーナーから聞き取った要件である。

## リリース判定との関係

[release-design.md](release-design.md) のリリース判定は、判断基準を先に設定に書き、集計と判定をスキルの固定コードが行い、悪化した項目を人がレビューし、記録を書き出してからレポートを書く。実験の仮説検証も同じ流れで書ける。違いは次の3点である。

| 観点 | リリース判定 | 実験 |
|------|--------------|------|
| 問い | 候補を出してよいか | 仮説どおり改善したか |
| 判定の言葉 | 出してよい／要レビュー／出さない | 実験の内容に合わせて AI が設定に書く（後述） |
| レポートの構成 | 結論、理由、注意点、次にやること | 背景と仮説、方法、結果、考察、結論と次にやること |

判断基準（`absolute`、`relative`、`regressions`、`critical_categories`）、指標の集計、「悪化」の定義、悪化項目のレビュー、記録の書き出し、frontmatter の判定とビルド時の照合は、リリース判定の仕組みをそのまま使う。同じことを書く方法を2つ作らないためである。

## 入力

データは今と同じく、ベースラインを `data.csv`、比べる条件を `data.candidates` に書く。項目は id で突き合わせる。

設定には、結果を見る前に決めた内容として次を書く。キー名は仮である。

```json
"experiment": {
  "hypothesis": "検索の再ランキングを入れると、正答率が上がり、遅延の悪化は 300ms 以内に収まる",
  "criteria": [
    {"type": "relative", "metric": "latency_ms", "max_worse": 300},
    {"type": "regressions", "max": 3}
  ]
}
```

`hypothesis` は画面とレポートの先頭に表示する。判断基準を設定に先に書かせるのは、結果を見てから基準を変えたことが、設定の変更履歴として残るようにするためである。

### 判定の言葉

判定は3段階で、内部ではリリース判定と同じ3つの状態（基準をすべて満たす／未レビューの悪化項目が残る／基準を満たさないか却下された項目がある）として扱う。画面とレポートに出す言葉は、実験の内容に合わせて AI が設定に書く（2026-10-11 リポジトリのオーナーが決定）。

```json
"verdict_labels": {"pass": "改善した", "review": "要レビュー", "fail": "改善しなかった"}
```

例：機能追加の実験なら「改善した／要レビュー／改善しなかった」、仮説が明確な実験なら「仮説を支持／要レビュー／支持しない」。3つとも空でない別々の文字列であることをビルド時に確かめる。レポートの frontmatter には言葉ではなく `pass` / `review` / `fail` を書き、ビルドで記録と照合する。

### 95%区間の扱い

差の95%区間は判断基準にしない。画面とレポートには目安として示し、区間をどう解釈して結論を出すかは人が決める（2026-10-11 リポジトリのオーナーが決定）。目安は次のとおり、各指標の行に文字で添える。

- 区間が0を含まない：差は誤差の範囲を超えている可能性が高い
- 区間が0を含む：差は誤差の範囲かもしれない

レポートの「考察」では区間を引用して解釈を書き、「結論と次にやること」で人が出した結論を書く。自動の判定と人の結論が食い違う場合（たとえば基準は満たしたが区間が0を含む）は、その旨をレポートに書く。

## 成果物

- `experiment` タブ：仮説、条件ごとの判定カード、条件 × 基準の表、各指標の n と95%区間、悪化項目のレビュー。リリースタブと同じ構成で、言葉だけを実験向けにする。
- 記録の書き出し（JSON / Markdown）：リリースの記録と同じ形式に `hypothesis` を加える。
- `report` タブ：レポートの Markdown を表示する。表示できる Markdown の範囲と、HTML タグを文字として表示する規則は今の `report` タブと同じである。
- レポートの Markdown 書き出し：`report` タブに「Markdown を書き出す」を置き、レポートの本文をそのまま書き出す。補助的な機能であり（2026-10-11 リポジトリのオーナーの判断）、グラフは書き出さず、貼り付け先での見え方の調整もしない。

レポートの構成（見出しはこの順）：

| 見出し | 内容 |
|--------|------|
| 背景と仮説 | 何を変えたか、なぜ改善すると考えたか。`hypothesis` を引用する |
| 方法 | データ（件数、ファイル名）、ベースラインと条件、指標、判断基準 |
| 結果 | 条件ごとの判定と、指標の値・差・95%区間。数値は記録から引用する |
| 考察 | 悪化した項目のレビュー結果、95%区間が0をまたぐ指標、件数の少ないカテゴリ |
| 結論と次にやること | 仮説を採るかどうかと、次の実験や作業 |

## 対象外

- ユーザーを群に分ける A/B テストのように、条件ごとに対象が異なるデータ。今の比較は同じ id の項目を突き合わせる前提であり、対応のないデータの集計と区間は別の設計になる。
- 実験の推移や過去の実験との比較。
- グラフを画像として書き出すこと（SKILL.md の対象外「charts meant for slides」と同じ理由）。

## 実装の形

`experiment` タブと `experiment` キーを新しく足し、集計・判定・レビュー・記録の処理はリリース判定と共有する（2026-10-11 リポジトリのオーナーが決定）。表示されるのは設定の `tabs` に書いたタブだけなので、実験の設定にリリースタブは出ず、リリース判定の設定にも実験タブは出ない。

検討して採らなかった案：`release` に判定の言葉とレポートの構成を切り替える設定を足し、タブ名は `release` のまま使う。コードは増えないが、実験なのにタブ名が「リリース」になる。

## 評価

架空データで、ベースラインと条件3つ（基準をすべて満たすもの、基準を満たさないもの、未レビューの悪化項目が残るもの）を用意し、評価ケースに追加する。レポートの例も1つ用意する。
